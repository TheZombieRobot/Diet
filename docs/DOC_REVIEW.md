# Document review (checklist item 1)

**Date:** 19 October 2026. **Status:** findings recorded; owner decisions pending where marked.

Checklist item 1 asks the implementer to read the eight planning documents and report anything that conflicts. Six independent readers each swept all the documents through a different lens (numbers and formulas; health wording against tests; fasting, weight and phases; data model completeness; technology and integration; process and file paths). Their 200 raw findings were merged into 118 distinct items, and every item was then checked by a separate skeptic who quoted the documents and tried to refute it. 113 were confirmed and 5 refuted.

How to read this file:
- **Needs the owner** items wait for the owner's decision. Each carries the implementer's recommendation; nothing is built on it until the owner answers.
- **Safe default** items are settled by the implementer in the most conservative way that contradicts no document, applied at the checklist item named. The planning documents are corrected when that item is built, and the correction is noted in the commit.
- Kinds: *conflict* (two statements cannot both be built), *gap* (unspecified but matters), *stale* (out-of-date reference), *technical* (conflicts with how the technology works today).

## Refuted by the skeptics (5)

- **C22** ABV unit is ambiguous: DATA_MODEL and PLAN write 'mL × ABV × 0.789 ÷ 1000' with a bare ABV, while REQUIREMENTS also gives a decimal form; the ÷1000 formula is 100× wrong if ABV is stored as a decimal. Why not a conflict: The quotes are verbatim: REQUIREMENTS 43, DATA_MODEL 22 and 31, PLAN 190 and HEALTH_SAFETY 108. The arithmetic is correct: 330 × 5 × 0.789 ÷ 1000 = 1.302, the same as the decimal form ÷ 10. But the docs are not ambiguous when read together. The ÷1000 form only makes sense with ABV as a percentage, and two docs say so explicitly: HEALTH_SAFETY 108 says 'volume in millilitres × alcohol percentage × 0.789 ÷ 1000', and REQUIREMENTS 43 pairs ÷1000 with 'ABV%'. DATA_MODEL's bare 'abv' is shorthand inside a formula whose divisor fixes the unit. The required AL-01 and HS-04 vectors (330 mL 5% = 1.30, and others) would fail immediately if a decimal were used with the ÷1000 form, so a mistake cannot pass silently. Item 4 has in fact already been built this way: packages/core/src/alcohol/standardDrinks.ts uses abvPercent, checks it is in 0–100, and computes mL × (abvPercent/100) × 0.789 ÷ 10. The proposed resolution also has a flaw: a warning when 0 < abv < 1 would fire on genuine low-alcohol drinks, and AL-01 itself includes '100 mL 0.5% = 0.04'.
- **C28** Eating window is derived from meal times in NN-02/HS-17 but stored as explicit start and end in targets; a single 23:1 meal gives 0 h, and start = end is undefined. Why not a conflict: The quotes are verbatim and correctly located, but the main claim is refuted. No doc derives the window from meal times as opposed to the stored window start and end. 'Computed from the clock times' (HEALTH_SAFETY line 66, DATA_MODEL line 32) refers to the window's start and end clock times, which are stored in targets (DATA_MODEL line 9). FL-08 ('Eating window 17:00-19:00'), FL-09 and UX 1e ('Eating 5:00 pm to 7:00 pm = 2 hours') all express it that way. NN-02's '5 pm snack + 7 pm final meal' is the 22:2 instance where the snack time is the window start and the final meal time is the window end. For 23:1, FL-14 explicitly gives a 6-7 pm window, so the '0 h eating' result only appears under a reading no doc requires. Treating the meal as an instant (22:2) versus a duration (23:1) is a convention the owner's requirement already fixes ('A 5-7 pm window is 22:2'), not a contradiction. What remains is that a custom window with start equal to end is undefined. That is input validation with no health effect, because either reading stays within the 24 h ceiling.
