# Bluetooth backup: hard problems, checked against the code

A review for step 1 of "Decided next (November 2026)" in [ROADMAP.md](ROADMAP.md) (messages without signal). Five readers each covered one area of the code and listed what is hard to get right; a skeptic checked every claim against the code (40 found: 31 confirmed, 9 corrected, 0 wrong) and a second reviewer added 5 problems that cut across areas. Line numbers refer to the code as of this commit.

Several of these are bugs in today's app, not only traps for the new feature: quick pings (including Need help) show as sent even when the upload failed and are dropped after 20 minutes; offline retries use up the relay's daily budget; any known key can start a rekey; check-ins arriving out of order raise false alarms; the intro advert carries a constant crew-pass prefix.

## The hard problems, most important first

### 1. One message id that survives re-sealing

Define one canonical message id used everywhere: gossip have/want sets, the outbox, the seen set and receivers. The id must stay the same across re-seals, so derive it from the signed content plus the sender's public key. Never use blob hashes, and don't add a signed field without a versioned plan, because History bundles, proofs and older builds would all break. Carriers forward the original bytes, since the signature binds the crew key and only the sender can re-sign. Persist the seen set and stop add() counting trimmed old lines as new.

Where to look: CrewChat.kt:49, :331-335, :557-576; ChatSync.kt:22-28, :54; GroupSync.kt:549; MailboxStore.kt:35; GigGroup.kt:194-198 (:196 crew-key HMAC), :284-365; CrewChat.kt:178-183

### 2. Forward-only delivery state: Sent nearby to Sent, without double-sending

Build a state machine that only moves forward (Waiting, then Sent nearby, then Sent) and decide how Sent is confirmed: your own message seen on the server by canonical id, an ack from a peer, or a byte-identical self-upload. Today markSeen hides the sender's own echo, add() never upgrades a line's state, and retryOutbox re-seals FAILED and stale SENDING lines. Store the original blob with the line, and give new states numbers after FAILED=2 so stored rows still load.

Where to look: CrewChat.kt:31-34, :292-296 (:294 markSeen), :351-359, :465-466, :561; ChatSync.kt:47, :54; RelayClient.kt:73-90

### 3. Removing a member offline: rekey hijack and the removed key never actually dropped

A rekey travels only over the internet, the payload names the removed person but not their key, receivers migrate with removedPub=null, and any known key may rekey. So a removed member nearby with no signal could push their own REKEY over Bluetooth. Decide who may rekey and the tie-break between concurrent rekeys, carry the removed public key(s), and allow an old-key grace window that uses an allowlist taken at rekey time, never a denylist. Decide what happens to queued old-key messages: only the sender can re-sign them.

Where to look: CrewRekey.kt:49, :62-69, :113, :127-133; CrewChat.kt:144-157; GroupSync.kt:274-282; ChatSync.kt:30-34; GigGroup.kt:196

### 4. Offline retries burn the public relay budget, so the first phone back can't upload

put() takes from the 200-a-day budget before it connects. LocationUploader retries on every fix, and retryOutbox, the intro and pings also retry offline, so after roughly 30 minutes without signal the budget is gone. Only charge the budget for requests that actually reach the relay, stop retry loops while there is no network (add a NetworkCallback and ACCESS_NETWORK_STATE), give put() separate results for sent, no network and throttled, and keep some budget back for the flush. Don't wait out 6+6 s timeouts before trying Bluetooth.

Where to look: RelayClient.kt:73-90 (:75), :352-386; LocationUploader.kt:52-59, :87-104; ChatSync.kt:47-50; CrewChat.kt:351-358; server Main.kt:39-40; no ConnectivityManager in app/

### 5. Delivery logic must live in core behind transport and clock interfaces

Only :core:test and :server:test can fail CI; Paparazzi and app tests are continue-on-error. Put routing, outbox, dedupe and state in core as a deterministic state machine with injected transports and per-phone clocks (core has no coroutines), so the simulation of three or more phones is a step(t) loop like CrowdRelayNetworkTest. The app keeps thin adapters only.

Where to look: .github/workflows/android.yml:84, :175-185; core/build.gradle.kts; CrewChat.kt:299-359; GroupSync.kt:531-545; core/src/test/.../CrowdRelayNetworkTest.kt:14-35

### 6. Quick pings have no outbox and receivers drop late ones

sendPing posts once, shows the line as SENT even if the post fails, and keeps no state. Receivers drop pings more than 20 minutes old, poll only the current and previous 5-minute epoch, and dedupe by blob hash, so a re-sealed copy alerts twice. Give pings the same outbox and states as chat, upload under the mailbox id that is valid at upload time, set a staleness policy per kind (never silently drop NEED_HELP), bound future timestamps, and dedupe by canonical id before notifying.

Where to look: GroupSync.kt:483-493, :515-523, :531-551; CrewChat.kt:526-531; MailboxStore.kt:16; RelayClient.kt:131

### 7. Check-in and Home safe reordering causes false urgent alarms

Check-in state is kept in memory, keyed by display name, and the deadline is the sender's timeSec plus minutes, checked against the receiver's clock. A HOME_SAFE that arrives before a delayed CHECK_IN brings the check-in back and every crew phone sounds an urgent alarm. Keep the newest state per sender tag by sender time, persist it, order the pings list by sender time with a 'late' marker, and give these pings top upload priority. Cover reordering and clock skew in the simulation.

Where to look: GroupSync.kt:571-579, :586-590, :593-601, :604-614, :551

### 8. Transport choice and radio coexistence (Nearby vs the app's own BLE)

The roadmap names Nearby Connections, but the app avoids Google Play services on purpose and already runs up to five advertisers, one shared scan limited to 4 starts per 30 s, UWB and Wi-Fi Aware. A failed advert just stops with no retry, so a new advertiser that takes the last slot makes the user unfindable. Nearby does not route over several hops. If Nearby is used: pin it to the version androidx.core.uwb resolves, check GMS availability, use no Wi-Fi upgrade (field-test that Aware survives), and diff the merged manifest. Phones without GMS or extended adverts must degrade cleanly. Record the reasoning for the owner.

Where to look: locate/MyLocation.kt:14-17; app/build.gradle.kts:118-142; gradle/libs.versions.toml:9; locate/BleBroadcaster.kt:38-42; locate/BleHub.kt:44-46; GroupSync.kt:729-731, :767; locate/CrowdRelayRadio.kt:58-61, :156; AndroidManifest.xml:5-7

### 9. The crowd relay can't carry signed pings or pins as it stands

RelayPacket is exactly 48 bytes, while a signed ping is 134-238 bytes, and many controllers cap an extended advert at about 251 bytes; oversized setAdvertisingData updates fail silently. RelayCache keeps the newest packet per id, accepts future times and evicts the smallest time. Helpers upload only with an own server, and old builds drop non-48-byte packets. Design a versioned packet and a separate message cache, a relay id that doesn't mark the crew, hop limits and stranger rate limits. Keep the existing relay tests passing.

Where to look: core/.../CrowdRelay.kt:17-21, :40-46, :55-81, :104-106; locate/CrowdRelayRadio.kt:95-102, :121-153; core/.../GigGroup.kt:135-136, :205-221; GroupSync.kt:535

### 10. New message kinds and formats vs older builds

onPing sends a 'pinged the crew' notification for any unknown kind, so new control kinds (acks, signed pins) sent as ping kinds would spam crew mates on older builds. CrewChat.ingest ignores quick pings, so pings moved to the held mailbox vanish. History has no version byte. Put new control messages in an envelope old builds can't open (a different AAD), add a known-kinds allowlist, and route every ingest path through one handler.

Where to look: GroupSync.kt:563-580, :618-654; GigGroup.kt:167-186, :224-259, :301-365; CrewChat.kt:457-487; ChatSync.kt:52-68

### 11. Pins: unsigned meet-up pin, MEET_AT_PIN without its pin, flares

The meet-up pin has no signature, and the newest sender time wins with no future cap, so anyone with the crew key can lock it with a far-future pin. MEET_AT_PIN carries the sender's location, not the pin, and flares are signed pings that are pins too. Define which pins are in scope, add a signed pin format with a compatibility plan and a skew cap, and make MEET_AT_PIN carry or reference the pin it means.

Where to look: GigGroup.kt:100-132; GroupSync.kt:470-473, :501-513, :665-699; MainActivity.kt:784-787, :1024-1027; CrewChat.kt:430-436, :472-480; docs/ROADMAP.md:89-94

### 12. Upload storm when everyone gets signal back

The server dedupes only byte-identical blobs and keeps 200 records per held id, ntfy doesn't dedupe at all, and per-IP limits are shared behind a venue NAT. shareHistory already re-uploads other people's lines in bundles. Decide how helpers avoid duplicate uploads (byte-identical forwarding, check before put, back-off with jitter), always use mailbox ids valid at upload time (chat polls today and yesterday), and treat History as an upload path.

Where to look: server/.../MailboxStore.kt:27-41; server/.../Main.kt:44, :134-166 (:156 takeLast(255)); CrewChat.kt:405-427; ChatSync.kt:49; RelayClient.kt:352-386

### 13. Lifecycle, persistence, threading and permissions

Start and stop message radio only in VisibilityService.begin()/onDestroy(), for the main crew, and never for followers or dormant crews. The activity holds GroupSync while not live. Don't add a new foreground service or type. Carried messages and seen ids must survive process death, with limits. Route Bluetooth callbacks to one thread, because CrewChat is safe only on Main. missingPermissions() skips BLUETOOTH_CONNECT and NEARBY_WIFI_DEVICES, and requiring them would block auto-go-live, so treat them as optional.

Where to look: service/VisibilityService.kt:84-161, :225-242, :245-266; GroupSync.kt:393-420; MainActivity.kt:421-435, :457-458, :1342-1345; CrewChat.kt:76; ChatSync.kt:24, :146-156; core/.../CrowdRelay.kt:55-58

### 14. On-air privacy and multi-crew matching

Nearby endpoint names and serviceIds must not identify the crew or the person. Prove crew membership after connecting with crew-key material, because Nearby's token is only a human-comparison string. Match frames to one of up to 30 crews without a stable tag. Consider padding sizes and randomising the starting ttl. The intro advert already leaks a constant crew-pass prefix; decide whether to fix it. Make the envelope reusable for private messages (step 4) without sealDirect's metadata leak.

Where to look: GigGroup.kt:47-56, :62-73 (:72), :216-221, :370-408; GroupSync.kt:440-455; docs/PRIVACY.md:31-34; core/.../CrowdRelay.kt:29; LocationUploader.kt:87

## Key facts by area

### Chat, pings, pins and the server mailbox

- Sealed crew messages are not tied to a mailbox, day or route, so another crew phone can upload a member's blob byte-for-byte. Ping format: [time:4][nonce:8][AES-GCM(kind,lat,lon,nameLen,name,minutes,textLen,text,pub:33,sig:64)+12-byte tag]. AAD is only the string "ping". The signature covers a value derived from the crew key plus every field (kind, timeSec, minutes, lat/lon, name, text). It does not cover the nonce, the mailbox id or the day. (core/src/main/kotlin/nz/waveformlabs/moshpoint/core/GigGroup.kt:194-198 (signedBytes, including hmac(key) at :196), :205-222 (sealPing; random nonce at :217; AAD at :220), :224-259 (openPing drops a message whose signature fails, :248))
- Sizes. A signed ping is 134 + name + text bytes: up to 238 for a quick ping (text cut to 80 bytes) and up to 318 for a chat line (text up to 160 bytes). A meet-up pin is 41 + name, so up to 65 bytes, and it is unsigned. A crowd-relay packet is a fixed 48 bytes (2 + 16-byte id + 30-byte LocationBox). (GigGroup.kt:186 (MAX_TEXT_BYTES=160), :488 (MAX_NAME_BYTES=24), :108-117 (sealRally); GroupSync.kt:536 (ping text cut to 80 bytes); core/.../CrowdRelay.kt:17-21,40; core/.../LocationBox.kt:40)
- Messages have no message-id field. Each re-seal produces new bytes, because the nonce is random and ECDSA (SHA256withECDSA) is randomized. A retry re-signs and re-seals, so its bytes never match the first attempt. The only content-stable identity is CrewChat.Line.key = sender|timeSec|text. That key leaves out kind, and quick pings and JOIN lines have an empty text, so they share the key shape sender|time|. (core/.../CrewKeys.kt:61-62; CrewChat.kt:49 (key), :331-335 (deliver re-seals), :530 (pingLine payload "" except check-in), :469 (JOIN text ""))
- Outbox states: SENT=0, SENDING=1, FAILED=2 (NOTE=99 is a kind, not a state). send() shows the line as SENDING and calls putHeld once; the result sets SENT or FAILED. retryOutbox re-sends (re-seals) up to 10 lines per crew that are mine, of kind CHAT, and either FAILED or SENDING for more than 60 s. It runs only inside ChatSync.pollAll. Only the line is saved (with its proof string), never the blob. Lines are kept as one tab-separated string per crew in SharedPreferences (8 columns, last 150 lines), and the whole string is rewritten on every add or state change. (CrewChat.kt:31-34, :78, :246-262, :304-313, :337-348, :351-359; ChatSync.kt:47)
- Chat mailbox: chatIdForDay(UTC day), daily HMAC id. Sends go to today's id; pollAll fetches today and yesterday for every crew in one lookupHeld. The public relay (ntfy) keeps 12 h and our own server 72 h. allCrews is the main crew plus Up next crews, up to 30, so 60 ids, which is exactly LOOKUP_CHUNK=60. (GigGroup.kt:139-140; CrewChat.kt:91,300; ChatSync.kt:30-34,49-50; RelayClient.kt:27,114-128)
- Server held mailbox: PUT /v1/held/{id} accepts 16 to 4000 bytes, TTL 72 h, at most 200 records per id (oldest dropped), at most 200k ids. A byte-identical PUT is idempotent: the old copy is removed and re-added at the front with a fresh timestamp. Re-sealed copies are stored as separate records. heldlookup takes at most 64 ids and returns held.get(id).takeLast(255) from a newest-first list, with a 1-byte count and 2-byte lengths. The PUT rate limit is a 120-request burst refilling at 2/s per client IP, taken from X-Forwarded-For. The ping/rally box /v1/box takes 16 to 255 bytes with a 15-min TTL. (server/.../MailboxStore.kt:15-41; server/.../Main.kt:37-44, :134-166, :199-205; RelayClient.kt:335-345)
- Public relay (ntfy) limits: each phone allows itself 200 messages a day and 8 requests a minute in total, shared by location posts, intros, pings and chat. A refusal, a 429 or a timeout all come back as false, so they look the same as having no signal. ntfy does not de-duplicate. Own-server PUT timeouts are 5 to 6 s for both connect and read. (RelayClient.kt:73-90, :308-319, :352-386)
- History bundles: every 4 h, plus a 0-60 min offset per phone, each phone posts a sealed History to today's chat mailbox, only if something is new. It holds the last 60 lines that are state==SENT and have a proof, plus the plan, deflated and cut down to 2,900 bytes. Lines with a location never get a proof, so they are never shared. Receivers check every line's signature (verifyLine) and read at most 500 lines. JOIN, NOTE, quick-ping and flare lines have no proof and are never in history. (CrewChat.kt:171-176, :405-427, :468-471; GigGroup.kt:284-288, :301-363, :487)
- Quick pings have no outbox, retry or state. sendPing works on the main crew only: it calls put once to pingIdForEpoch (rotates every 5 min) and only logs a failure. Receivers poll the current and previous epoch only, drop pings more than 20 min old, de-duplicate by blob hashCode in an in-memory set, and drop unsigned or own pings. The chat bubble (pingLine) is added as mine/SENT straight away. (GroupSync.kt:483-493, :515-523, :528-546, :548-551; core/.../EphemeralId.kt:55; CrewChat.kt:526-531)
- The meet-up pin (rally) is unsigned and anyone with the crew key can forge it. The newest timeSec wins, including removals (rallyClearedAt). It goes to rallyIdForDay. The owner reposts every 10 min. Lookups cover today and yesterday. The app has no ConnectivityManager or NetworkCallback anywhere and no Nearby Connections dependency, so 'back on signal' is only noticed at the next poll: about 10 s with the chat open, about 2 min with the app open, about hourly as an inexact alarm in the background. (GigGroup.kt:101-132; GroupSync.kt:470-473, :504-513, :665-699; ChatSync.kt:146-156; GroupSync.kt:491,516; MainActivity.kt:496,989; grep for ConnectivityManager/NetworkCallback/nearby finds nothing in app/)

### Identity, keys and privacy

- A signed crew message is self-verifying offline: the 33-byte compressed P-256 public key and 64-byte raw r||s signature ride inside the crew-key AES-GCM plaintext. The signature covers 'mp-sig1', 8 bytes of HMAC(crewKey,'moshpoint-group-sig'), kind, time, minutes, lat/lon, name and text. It has no message id or nonce, and it is bound to the current crew key, so a line signed under the old key fails verifyLine after a rekey. A signed ping with an empty name and no text is already about 134 bytes. (core/.../GigGroup.kt:194-198 (signedBytes), :205-222 (sealPing layout), :245-250 (verify inside openPing), :284-288 (verifyLine uses this.key); CrewKeys.kt:32-33,61-70)
- Core openPing still accepts unsigned pings (sender=0). A bad signature returns null, so the whole message is dropped. The app drops unsigned pings at two separate places, so any new Bluetooth ingest path must repeat that check itself. (GigGroup.kt:243-257; GroupSync.kt:550; CrewChat.kt:459)
- Crew membership works on first sight. Any key that ever signed a valid message under the crew key goes into knownKeys. So a signature proves only 'holds the crew key and this keypair', not 'is an approved member'. Followers (watching from home) hold the full crew key but never use Bluetooth. (CrewChat.kt:121-133 (knownKeys/rememberKey), :457-461 (ingest calls rememberKey); GroupSync.kt:420,450 (followers skip BT); GigGroup.kt:547-551)
- Each crew gets its own signing key, stored as plain base64 PKCS8 in SharedPreferences (not Keystore). The same signing key is deliberately kept across a rekey. The crew pass (finding identity) is HMAC(permanent secret, crewKey), so it changes with every crew and every rekey. (Identity.kt:28-30, 47-59, 75-80; docs/ARCHITECTURE.md:111 (Keystore still a to-do))
- A rekey creates a random 32-byte key. It is sent as a sealDirect kind=3 sealed under the OLD crew key, only through RelayClient.putHeld (internet), and re-sent every 6 h for 72 h. The payload is newKey plus the removed person's NAME, not their public key. Receivers migrate with removedPub=null, and CrewChat.migrate copies the 'keys' and 'people' maps. So on every phone except the remover's, the removed member's key stays a known member of the new crew. (CrewRekey.kt:26-28, 40-58 (payload line 49), 94-118 (putHeld only, line 113), 123-137 (migrate(app,g,fresh,null) line 133); CrewChat.kt:144-157; GroupSync.kt:274-282 (only removes when removedPub != null))
- CrewRekey.onDirect accepts a REKEY from ANY key in members(g), which comes from knownKeys plus GroupSync pubs. That includes the member being removed, while they still hold the old key. The only guard is 'already have this exact new key'. After migrating, the old crew is no longer polled, so whichever REKEY arrives first wins. (CrewRekey.kt:62-69, 127, 129; ChatSync.kt:30-34, 66-67)
- Replay and duplicate handling is weak. ChatSync.seen and GroupSync.seenPings are in-memory sets of 32-bit blob contentHashCode. Pings older than 20 min are dropped, and there is no limit on future timestamps. Chat lines are deduped persistently by 'sender|timeSec|text'. Every retry re-seals with a fresh random nonce, so the same message gets new blob bytes. (ChatSync.kt:22-28, 54; GroupSync.kt:548-551; CrewChat.kt:49 (Line.key), 292-296 and 331-335 (deliver re-signs/re-seals))
- The crowd relay format is fixed. RelayPacket is exactly 48 bytes (version, cleartext ttl, 16-byte id, 30-byte LocationBox). RelayCache keeps only the NEWEST packet per id, holds at most 300 entries for at most 10 minutes, and the id is not authenticated. Phones that hear a packet upload it only when an own server is configured (never to ntfy.sh). (core/.../CrowdRelay.kt:17-48, 55-81, 102-108; CrowdRelayRadio.kt:95-102, 142-164)
- Crew intros are broadcast over BLE extended adverts every 2.5 s, alternating with re-broadcasts of other members' intros. Each blob starts with a crew-wide 8-byte tag (the same for every member in a 5-minute epoch), then a 4-byte timestamp, then the first 4 bytes of the member's crew pass IN THE CLEAR. That pass stays the same for the whole gig. (GigGroup.kt:47-56, 62-73 (line 72 appends intro.secret.copyOf(4)), 460-462; GroupSync.kt:428-455)
- Private-message building blocks already exist. sealDirect is static-static ECDH (SHA-256 with 'moshpoint-direct'), AES-GCM inside, crew-key AES-GCM outside.
