# Reliability audit (ccr 792cd68, 15 Nov 2026), condensed from the auditor's report

Tags: [effort · changes behaviour the owner would notice]

## P0
1. Live can show on with nothing running. Nothing reconciles VisibilityPrefs.visible with the real service. A Play update, force-stop, OEM kill or revoked permission leaves the flag on. MainActivity.onResume (544–551) then skips the restart and the tile shows on. BootReceiver ignores MY_PACKAGE_REPLACED. VisibilityService.onStartCommand (56–62) gives up silently when a restart is refused. Fix: on foreground, restart the service if the flag says live and it isn't running; handle MY_PACKAGE_REPLACED; post a "You're no longer live" notification when a restart is refused. [S · yes] High confidence (every update).
2. Need help says "Crew alerted ✓" before it's sent. HelpDialog (CrewChatUi 477–490) flips the label on tap. GroupSync.sendPing (590–605) ignores OfflineMessages.post refusing. Not live with no signal, the Bluetooth radio is off, so the alert sits queued. Safety.textContact/callEmergency (39–52) fail silently on a phone with no SMS or dialler app. The watch already reports honestly (WatchPings). Fix: show the real outbox state (Sending / Not sent yet + Go live / Sent nearby / Sent), "Not sent" on refusal, and a message when text or call can't open. [S–M · yes]
3. The relay forgets accepted messages. fly.toml: auto_stop_machines="stop", min_machines_running=0, 256 MB; Render free plan sleeps. Every store is in memory (moshpoint(), Main.kt 39–50) and files go to /tmp, so any idle stop, deploy or crash wipes 3-day chat, pins, rosters and safety pings already shown as Sent. PUT /v1/file (Main 116) and FileStore.get hold a whole 12 MB file in memory against a ~100 MB default heap (OOM threshold not confirmed). Courier re-posts dropped pins (Courier 402–410) but not our own safety pings. Fix: one always-on machine with ~1 GB; SQLite on a volume for chat and pings; stream files to disk; Courier re-uploads own safety pings found missing; fail release builds when MOSHPOINT_SERVER is empty (otherwise the app silently uses public ntfy.sh). [M · hosting cost only]
4. Overdue check-in only fires on phones that are open or live. GroupSync.checkOverdue only runs from syncServer (533) and followers' 15-min check; ChatCheckReceiver never calls it and nothing schedules the deadline. FEATURES.md promises the timer runs on the crew's phones. The alert uses the default-priority "crew" channel shared with chat (694), so muting chat mutes it. Fix: when a check-in arrives, set a Doze-capable alarm (setAndAllowWhileIdle, RTC_WAKEUP) for its deadline that loads the crew, checks for Home safe, then runs checkOverdue; also call it from ChatSync.runInBackground; post on "crew_help". [M · yes]

## P1
5. Background checks die on reboot and stall in Doze. BootReceiver only restarts the service. ChatSync.schedule is only set when a crew is made or joined (GroupSync 261, Crews 83), never at app start. FollowCheck only comes back when the app opens (MainActivity 573). Both use inexact ELAPSED_REALTIME (FollowCheck 24, ChatSync 215), so a follower's 15-min check can run hours late. Fix: re-arm everything on boot, update and app start; Doze-capable wake-up alarms for followers; relay push later. [S, push L · alerts sooner]
6. Full storage gives a crash loop. Unguarded writes: FriendsRepository.save (Friends 194–199), Moments.unpackClip (171) in the GroupSync loop, PhotoStore.save (98) via AvatarSync. No CoroutineExceptionHandler on long-lived scopes, so one failure kills the app (live service included) on every sync. OfflineMessages.save hides its failures, so the outbox silently stops persisting. Fix: guard the writes, add a logging handler to every background scope, tell the user storage is full. [S · none]
7. Activity recreation closes the finder. No configChanges in the manifest; finding/showMap/showChat/beaconOn are plain MainActivity and MomentFlow fields. Scheduled dark mode or Bedtime (often ~11 pm), language or font change, split screen and foldables end a find in progress, stop Light me up and restart scans. A recorded clip (MomentFlow.clipFile) is lost if the camera app's memory kills ours. targetSdk 36 will ignore the portrait lock on large screens. Fix: declare configChanges (Compose copes), or ViewModel/rememberSaveable. [S–M · none]
8. CrewRadar can crash while drawing. CrewRadar 246–247, 264–265: coerceIn(chipW/2+pad, size.width-chipW/2-pad) throws when the radar is under about 88×44 dp (possible on a small phone with a large font while banners show). Fix: centre when the range is empty. [S · none] Medium confidence.
9. The server can't cope with crowds or abuse. client() (Main 64–66) trusts the first X-Forwarded-For entry, which the client can set. A venue behind one address shares 1 lookup/s and 2 uploads/s, which the crowd relay's background uploads use up. Stores cap mailbox counts, not bytes; GigSearch.cache is unbounded. VenueLookup.find, GigSearch.search and FileStore.put block request threads on one CPU. Fix: use Fly-Client-IP, limit per mailbox, cap bytes, move blocking work to Dispatchers.IO. [M · none] Needs a load test.

## P2 ([S · none] unless noted)
- handleInvite (MainActivity 394–398): an invite naming a relay (r=) silently moves every crew to it. [yes]
- FriendRecord.parse drops crew mates added more than 18 h ago, so a planned crew loses its faces after a restart. [yes]
- Clocks: syncServer only looks up the current and previous 5-min ids (a mate whose clock is >5 min fast can't be found by GPS); LocationBook.update takes future timestamps; a clock jump forward makes loadCrews end the crew and delete its data.
- Memory: the Story holds up to 400 decoded 640–1024 px thumbnails (Moments.items); PhotoStore.setShared decodes mates' photos at full size; the 8+n size sum in Moments.unpackClip can overflow, so one crew member can crash everyone's app; 12 MB file copies run on the main thread.
- Courier.restore and PrivateBook.restore throw away everything when SAVE_VERSION changes.
- GigArchive.keep writes the photo before indexing it, so a crash in between leaves it out of the Story.
- Nothing ever cleans gigs/, cache/clips or expired Up next chat files.
- ChatCheckReceiver's goAsync work has no time limit (ANR on a slow network).
- The live notification still says "You're live" with Bluetooth off.
- Uncaught ISE in CrowdRelayRadio.startBroadcasting and in the VisibilityTile.onClick service start.
- Release builds report no errors at all: add privacy-safe error counts.

## Done well
Courier puts safety first, saves atomically, never moves a state backwards and lets Need help through rate-limit pauses (sim-tested); the watch's Need help reports the true outbox state; finder and Bluetooth state stay on the main thread and BleHub stays within the scan-start limit; parsing of adverts, QR codes, invites and relay replies is defensive; format placeholders match in all 19 translations.
